# Dynamic GUI & Design System Specifications

## 1. Overview & Execution Authority
* **Design Philosophy:** Clean, modern, accessible, and responsive clinical-campus healthcare portal.
* **Kiro Autonomous View Generation:** Kiro is explicitly authorized to design, create, and adapt any EJS views (`views/**/*.ejs`) and CSS rules needed to support backend features.
* **Adaptability:** Wireframes, images, or layout sketches are targets for structural inspiration. Kiro may improve layout semantics, spacing, form controls, and card structures to fit the live data.

## 3. UI/UX Rules & View Responsibilities

### A. Dynamic View Creation Directive
When executing any feature specification (e.g., Symptom Checker, Booking, Nurse Dashboard), Kiro **must automatically build or update the required EJS views** within their respective role folders:
* Student Views: `views/student/`
* Nurse Views: `views/nurse/`
* Admin Views: `views/admin/`
* Authentication Views: `views/auth/`
* Shared UI Components: `views/partials/`

### B. View Layout Standards
1. **Header & Navigation:** Every full page view must include the dynamic header and navbar partials (`views/partials/header.ejs`, `views/partials/navbar.ejs`).
2. **Card-Based Interface:** Information and forms must be grouped logically inside visually distinct white cards with soft shadows (`box-shadow: 0 4px 6px -1px rgba(0,0,0,0.1)`).
3. **Form Safety & Feedback:** * Form inputs must include clear label tags, placeholder hints, and client-side HTML5 validation attributes (`required`, `min`, `max`).
   * Views must gracefully render alert feedback blocks when backend controllers pass error or success messages in `res.render()`.
4. **Data Presentation:** Data lists must use responsive grid cards (for mobile/desktop flexibility) or clean styled tables with hover highlights (`table-hover`).
