The Comprehensive Engineering & Architectural Specification: CampusCare Hub System Context
Section 1: Executive Summary & System Philosophy
CampusCare Hub is an enterprise-grade, web-based healthcare management platform designed specifically to mitigate university clinic congestion and modernize student health services through a structured Three-Tier Healthcare Strategy. Built on a Model-View-Controller (MVC) architectural pattern using modern ES Modules, Express.js, MySQL, and EJS templating, the system establishes a clear separation of concerns, strict database security guarantees, and granular Role-Based Access Control (RBAC).

The Three-Tier Healthcare Strategy
1. Tier 1 (Automated Support & Self-Care): Focuses on initial triage. Students self-report symptoms through an intelligent lookup system, receive over-the-counter (OTC) medication guidance mapped to campus distribution facilities, and view anonymized regional health trend maps to track campus outbreaks.
2. Tier 2 (Nurse Consultations): Facilitates direct clinical care. When self-care is insufficient or symptoms indicate moderate severity, students can schedule 15-minute physical appointments at local clinics or online consultations integrated with Microsoft Teams meeting links. Post-consultation feedback mechanisms allow students to submit numerical ratings and qualitative performance reviews.
3. Tier 3 (Clinical Escalation & System Administration): Manages administrative oversight and acute care. Nurses control daily shift schedules, manage real-time patient progress, approve online video sessions, and escalate complex cases. System administrators gain real-time visibility through aggregate reporting metrics to optimize healthcare operations.
Section 2: Core Technical Stack & Architectural Guidelines
1. Technology Infrastructure
* Runtime Environment: Node.js (v18+) configured with native ES Module syntax ("type": "module" declared within package.json).
* Application Framework: Express.js (v4.x) serving as the HTTP routing engine.
* Templating & Presentation Engine: EJS (Embedded JavaScript Templates) utilizing reusable header/footer layouts, partials, and standard HTML5/CSS3 components.
* Persistence Layer: MySQL 8.0+ managed via the mysql2/promise asynchronous driver. Database connections are sustained through a centralized, continuous pool configuration located at src/config/database.js.
* Session Management & Security: express-session configured with httpOnly: true, resave: false, saveUninitialized: false, and dynamic secret keys to prevent cookie manipulation and session hijacking.

3. Security Requirements
* SQL Injection Prevention: Direct string concatenation within SQL statements is strictly prohibited. Every model function must execute queries using parameterized positional placeholders (?) passed alongside sanitized data arrays.
* Cross-Site Scripting (XSS): Inputs collected via POST/PUT actions must undergo server-side validation and sanitization before processing or DB insertion. HTML output rendered in EJS views must use standard escaping (<%= %>).
* Role-Based Access Control (RBAC): All protected routes must invoke explicit middleware guards prior to processing requests:
   * requireAuth: Verifies active session presence (req.session.user).
   * requireStudent: Enforces active student session (role === 'student').
   * requireNurse: Enforces nurse permissions (role === 'nurse').
   * requireAdmin: Enforces administrative permissions (role === 'admin').

Table Specifications
1. Student
* StudentNumber (VARCHAR(50), Primary Key): Unique university student identification string.
* FirstName (VARCHAR(100)): Student given name.
* LastName (VARCHAR(100)): Student surname.
* Address (TEXT): Residential address or campus hostel identifier.
* MedicalHistory (TEXT): Encrypted or structured text of pre-existing conditions and allergies.
* Password (VARCHAR(255)): Password digest.
2. Nurse
* StaffNumber (VARCHAR(50), Primary Key): Unique clinical staff member ID.
* FirstName (VARCHAR(100)): Staff given name.
* LastName (VARCHAR(100)): Staff surname.
* ClinicID (INT, Foreign Key $\rightarrow$ Clinic.ClinicID): Assigned primary clinic location.
* Password (VARCHAR(255)): Password digest.
3. Admin
* AdminID (VARCHAR(50), Primary Key): Unique system administrator identifier.
* FirstName (VARCHAR(100)): Administrator given name.
* LastName (VARCHAR(100)): Administrator surname.
* Password (VARCHAR(255)): Password digest.
4. Symptoms
* SymptomCode (VARCHAR(50), Primary Key): Standardized symptom classification code (e.g., SYM-FVR-01).
* Name (VARCHAR(100)): Human-readable symptom name (e.g., "High Fever").
* Description (TEXT): Detailed clinical description and indicators.
* Type (VARCHAR(50)): Category (e.g., "Respiratory", "Gastrointestinal", "Neurological").
* Tier (INT): Severity classification level (1 = Self-care, 2 = Clinical consult, 3 = Urgent hospital care).
* Cause (TEXT): General medical triggers or potential underlying pathogens.
5. Medication
* MedicationCode (VARCHAR(50), Primary Key): Standard pharmaceutical identifier code.
* Name (VARCHAR(100)): Brand or generic medication name (e.g., "Paracetamol 500mg").
* Description (TEXT): Usage instructions, dosage guidelines, and drug warnings.
* SymptomsTreated (TEXT): Summary of target conditions.
* ExpiryDate (DATE): Inventory expiration tracking date.
* FacilityID (INT, Foreign Key $\rightarrow$ MedicalFacility.FacilityID): Dispensing inventory location.
6. SymptomMedication
* SymptomCode (VARCHAR(50), Foreign Key $\rightarrow$ Symptoms.SymptomCode): Associated symptom.
* MedicationCode (VARCHAR(50), Foreign Key $\rightarrow$ Medication.MedicationCode): Associated OTC drug.
* Composite Primary Key: (SymptomCode, MedicationCode).
7. Appointment
* AppointmentID (INT, Auto-Increment Primary Key): Unique consultation record.
* AppointmentType (VARCHAR(50)): Delivery format (Physical or Online).
* Time (DATETIME): Scheduled consultation timestamp.
* TeamsID (VARCHAR(255)): Microsoft Teams join URL or meeting identifier (populated for online sessions).
* Status (VARCHAR(50)): State machine tracking (Pending, Confirmed, Completed, Cancelled).
* StudentNumber (VARCHAR(50), Foreign Key $\rightarrow$ Student.StudentNumber): Patient reference.
* StaffNumber (VARCHAR(50), Foreign Key $\rightarrow$ Nurse.StaffNumber): Clinical staff reference.
8. Rating
* RatingID (INT, Auto-Increment Primary Key): Feedback entry identifier.
* Score (INT): Numerical score (Scale 1 through 5).
* RatingDescription (TEXT): Qualitative student feedback narrative.
* AppointmentID (INT, Foreign Key $\rightarrow$ Appointment.AppointmentID): Associated completed visit.
* StudentNumber (VARCHAR(50), Foreign Key $\rightarrow$ Student.StudentNumber): Reviewer reference.
9. Clinic & MedicalFacility
* ClinicID / FacilityID (INT, Primary Key): Primary physical location references.
* Name (VARCHAR(100)): Facility title (e.g., "Main Campus Student Clinic").
* Location (VARCHAR(255)): Physical geographic coordinates or campus address.

Module 01: Authentication, Profiles, and System Access
* Assigned Team Member: Tarisai Rusike
* Use Cases Addressed: C100, E100, E200, E300, E400
* Target Domain: User onboarding, credential authentication, session tracking, profile customization, and account destruction.
Functional Requirements (requirements.md)
1. Student Registration (C100): Prospective students must register using their unique StudentNumber, FirstName, LastName, physical Address, pre-existing MedicalHistory, and password. Duplicate student numbers must be caught server-side and trigger a user-friendly error response.
2. Multi-Role Authentication (E100/E400): The system must provide a unified or role-selectable login portal. Users select their identity context (student, nurse, admin), submit primary key credentials (StudentNumber, StaffNumber, or AdminID) alongside their password, and upon validation, receive a server-signed session (req.session.user).
3. Profile Access & Editing (E300/E400): Authenticated students must be able to view their profile attributes and update dynamic information (Address, MedicalHistory). Core primary identifiers (StudentNumber) remain read-only.
4. Account Destruction (E200): Authenticated students can request account deletion. The controller must remove the record from the Student table, destroy the active session context, and redirect to the public home page.
Design Specification (design.md)
* Model Layer (src/models/userModel.js):
   * findStudentById(studentNumber): Runs SELECT * FROM Student WHERE StudentNumber = ?
   * findNurseById(staffNumber): Runs SELECT * FROM Nurse WHERE StaffNumber = ?
   * findAdminById(adminId): Runs SELECT * FROM Admin WHERE AdminID = ?
   * createStudent(data): Runs INSERT INTO Student (StudentNumber, FirstName, LastName, Address, MedicalHistory, Password) VALUES (?, ?, ?, ?, ?, ?)
   * updateStudentProfile(studentNumber, { address, medicalHistory }): Runs UPDATE Student SET Address = ?, MedicalHistory = ? WHERE StudentNumber = ?
   * deleteStudentAccount(studentNumber): Runs DELETE FROM Student WHERE StudentNumber = ?
* Controller Layer (src/controllers/authController.js & profileController.js):
   * showLoginForm: Renders views/auth/login.ejs.
   * handleLogin: Extracts role and credentials, calls targeted user model, matches password digest, sets req.session.user, and routes to dashboard.
   * showRegisterForm: Renders views/auth/register.ejs.
   * handleRegister: Validates input length/format, verifies non-existence via findStudentById, invokes createStudent, and redirects to login.
   * handleLogout: Invokes req.session.destroy() and clears session cookie.
   * showProfile: Pulls ID from active session, queries student details, renders views/profile/view.ejs.
   * updateProfile: Validates updated text strings, invokes updateStudentProfile, updates session values, and redirects.
   * deleteAccount: Executes deleteStudentAccount, destroys session, and returns redirect response.
* Route Configuration (src/routes/authRoutes.js & profileRoutes.js):
   * GET /auth/login
   * POST /auth/login
   * GET /auth/register
   * POST /auth/register
   * POST /auth/logout
   * GET /profile (Secured via requireAuth)
   * POST /profile/update (Secured via requireStudent)
   * POST /profile/delete (Secured via requireStudent)
Module 02: Symptom Checker & OTC Recommendations
* Assigned Team Member: Vhuthuhawe Nekhavhambe
* Use Cases Addressed: A100, A200, A300
* Target Domain: Automated symptom catalog browsing, multi-factor symptom evaluation, Over-The-Counter (OTC) drug matching, distribution facility mapping, and Tier 2 clinical escalation triggers.
Functional Requirements (requirements.md)
1. Symptom Catalog Browsing (A100): Students must be able to view and filter the master list of tracked symptoms (Symptoms table) organized alphabetically or by body system Type.
2. Symptom Input & Tier 1 Evaluation (A200): Students select observed symptoms and indicate current severity level (e.g., Low, Moderate, High). The controller processes these selections against symptom tier classifications (Tier).
3. OTC Medication Guidance (A300): The system performs join queries against SymptomMedication, Medication, and MedicalFacility tables to output recommended OTC treatments, dosage instructions, expiration safeguards, and physical campus pickup locations.
4. Clinical Warning Guards: If evaluated symptom tiers return $\ge 2$ or severity is classified as "High", the recommendation view MUST highlight a prominent warning message prompting the student to immediately schedule a Tier 2 physical or online consultation.
Design Specification (design.md)
* Model Layer (src/models/symptomModel.js):
   * getAllSymptoms(): Runs SELECT * FROM Symptoms ORDER BY Name ASC
   * getSymptomByCode(symptomCode): Runs SELECT * FROM Symptoms WHERE SymptomCode = ?
   * getMedicationsForSymptom(symptomCode): Executes relational query:
SQL
SELECT m.MedicationCode, m.Name AS MedicationName, m.Description, 
      m.SymptomsTreated, m.ExpiryDate, mf.Name AS FacilityName
FROM Medication m
INNER JOIN SymptomMedication sm ON m.MedicationCode = sm.MedicationCode
LEFT JOIN MedicalFacility mf ON m.FacilityID = mf.FacilityID
WHERE sm.SymptomCode = ?;

   * Controller Layer (src/controllers/symptomController.js):
   * renderSymptomForm: Calls getAllSymptoms() and renders views/student/symptom-form.ejs.
   * processSymptomCheck:
   1. Extracts symptomCode and user-submitted severity rating from req.body.
   2. Queries detailed metadata via getSymptomByCode.
   3. Fetches drug recommendations via getMedicationsForSymptom.
   4. Evaluates tier logic (if (symptom.Tier >= 2 || severity === 'High') { escalate = true }).
   5. Renders views/student/recommendations.ejs passing symptom detail objects, drug lists, and escalation flags.
   * Route Configuration (src/routes/symptomRoutes.js):
   * GET /symptoms (Secured via requireStudent)
   * POST /symptoms/evaluate (Secured via requireStudent)

Design Specification (design.md)

   * getSymptomAggregation(): Executes grouping query:
SQL
SELECT s.Name AS SymptomName, s.Type, COUNT(sm.MedicationCode) AS LogCount
FROM Symptoms s
LEFT JOIN SymptomMedication sm ON s.SymptomCode = sm.SymptomCode
GROUP BY s.SymptomCode, s.Name, s.Type
ORDER BY LogCount DESC;

Section 6: Operations & Deployment Runbook
1. Local Development Initialization
To initiate the CampusCare Hub application locally in a development environment:
            1. Provision a local MySQL database instance matching the schema structure.
            2. Configure environment variables (.env) for DB connection parameters (DB_HOST, DB_USER, DB_PASS, DB_NAME, SESSION_SECRET).
            3. Execute database seed scripts:
Bash
npm run db

            4. Start the Node.js server engine:
Bash
npm start

2. Error Handling & Exception Flow Standards
To guarantee enterprise reliability and prevent system crashes:
               * All asynchronous controller code must wrap DAO calls within try/catch blocks.
               * Database failures or connection pool dropouts must be caught gracefully, logging internal details to server logs while presenting clean, non-technical error alerts to users.
               * Unhandled exception stack traces must never be exposed within rendered HTML responses in production environments.
